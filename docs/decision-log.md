# Architecture Decision Log

Record material decisions with date, status, context, options, decision, consequences, and links to related phases. Do not log routine implementation details here. Proposed or open entries are not approved decisions.

## D-001 — Shared domain model for bicycle variants
- **Status:** Proposed
- **Context:** Five bicycle variants need distinct visuals while sharing repair content where components are equivalent.
- **Decision:** Keep SVG presentation and hit-region mappings separate from the shared component, symptom, and guide model.
- **Consequences:** The same repair guide can be reused safely, while variant-specific components and unknown compatibility are explicit.
- **Validation needed:** Confirm mappings and absent/optional components in all five SVG variants.

## D-002 — Deterministic MVP diagnosis
- **Status:** Proposed
- **Context:** Core functionality must work without a remote model or provider key.
- **Decision:** Use testable deterministic rules first; consider AI-assisted retrieval only after guide content and baseline behavior are stable.
- **Consequences:** Diagnosis is reproducible and can act as a baseline for evaluating any later AI assistance.

## D-003 — Durable repair-request submissions
- **Status:** Implementation in progress; production configuration and policy gates remain open
- **Context:** The user must be able to ask the developer for missing guide content.
- **Decision:** Persist requests privately before showing recorded success; isolate notification delivery and provide failure recovery.
- **Consequences:** Hosting, persistence, access controls, notification configuration, and operational monitoring must be verified before production claims.

## D-004 — Application foundation stack
- **Status:** Approved for the provided starter on 2026-10-28; dependencies not yet installed locally
- **Context:** The provided BikeFix target contained documentation and directory placeholders, without application source, a package manifest, lockfile, or Git metadata. The owner approved proceeding with the previously recommended Next.js foundation.
- **Decision:** Use Next.js App Router, React, TypeScript, Tailwind CSS 4, npm, Vitest/Testing Library, and Playwright as the initial stack. The starter pins Next.js 16.4.3, React/React DOM 19.3.1, and Tailwind CSS 4.3.3 in `package.json`; other tooling uses compatible semver ranges. The project Node minimum is 22.12.0 because the selected Vitest 5/Vite toolchain requires it.
- **Consequences:** A reproducible `package-lock.json` must be generated by a successful `npm install` and committed after installation. Do not claim a successful build until the configured checks actually run.
- **Open:** Hosting provider is still unconfigured. The current file store is local-development/self-hosted only and production route activation is fail-closed. Confirm the persistent host and all production gates before enabling submissions. This decision applies to the provided starter only, not to any separate repository that might later be connected.

## D-005 — Repair-request retention and deletion
- **Status:** Open — blocks production submissions
- **Context:** Repair requests may contain descriptions and optional contact information. A retention duration must reflect the product's operational purpose and appropriate privacy review.
- **Decision needed:** Product owner approves a retention period, treatment of unresolved requests, deletion/anonymization procedure, operator access, and backup-retention limitations. Do not invent a legal retention period or imply compliance without review.
- **Acceptance evidence:** Approved policy documented in `docs/request-workflow.md` and the public privacy notice, plus a passing deletion/retention test or verified documented operator procedure.

## D-006 — Notification status semantics
- **Status:** Implemented in source; production provider verification remains open
- **Context:** Successful persistence, provider acceptance, email delivery, and recipient reading are different events.
- **Decision:** Persist the request before notification; track notification results separately; report only states supported by provider evidence; retain and recover requests when notification fails.
- **Acceptance evidence:** Provider-specific behavior documented; tests distinguish provider-accepted from delivered and failed states; the Resend idempotency key reduces duplicates within its documented 24-hour window. Real sender/provider configuration and any delivery-webhook behavior remain unverified until production setup.

## D-007 — Initial repair-guide catalog ownership
- **Status:** Approved planning rule
- **Context:** Both the player phase and content phase previously claimed responsibility for the eight initial guides.
- **Decision:** Phase 06 owns the guide player and representative fixture content. Phase 07 owns authoring, sourcing, validation, and review status of the eight-guide catalog.
- **Consequences:** The player can be tested before content production, while initial content has one responsible phase.

## D-008 — Phase 08 local/private request adapter and production gate
- **Status:** Implemented for local development; production backend/host decision remains open
- **Context:** The request workflow needs persistence and notification adapters before a hosting provider is approved. A frontend-only form would be false completeness, while selecting a managed database or service without owner approval would add unapproved infrastructure.
- **Implementation:** Use a file-per-record store under a private directory for local development and verified self-hosted Node hosts with persistent volumes. Use server-side Zod validation and an optional Resend REST notification adapter. The request route is disabled in production unless a private absolute storage path, durable-volume confirmation, approved retention/cleanup, access/audit, edge rate-limit, and notification configuration gates are present.
- **Consequences:** Local workflow behavior can be tested without credentials. Production deployment is not ready by default; ephemeral filesystems are unsupported. Notification accepted status is not delivery. Retention approval must precede production collection.
